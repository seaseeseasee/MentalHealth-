# Phase 3: รายการ KPI และสูตรคำนวณ (ตามที่พัฒนาจริง)

โค้ดอ้างอิง: `api/src/analytics.ts` (สูตรทั้งหมด), `api/src/admin.ts` (API และสิทธิ์)

## หลักการร่วมของทุกตัวชี้วัด

| หลักการ | วิธีทำในระบบ |
| --- | --- |
| เวลา | เก็บเป็น UTC แต่จัดกลุ่มเป็น **วันตามเวลาไทย (UTC+7)** ทุกจุด ช่วง `from`–`to` เป็นวันไทยแบบรวมวันสุดท้าย |
| ช่วงเวลา | ทุก API รับ `?from=YYYY-MM-DD&to=YYYY-MM-DD` ค่าเริ่มต้น 30 วันล่าสุด ช่วงยาวสุด 5 ปี วันที่ผิดรูปแบบตอบ 400 |
| คนกับครั้ง | "คน" ใช้ `COUNT(DISTINCT user_id)` เสมอ "ครั้ง" ใช้ `COUNT(*)` แสดงแยกกันทุกที่ |
| เริ่มทำกับสำเร็จ | เริ่มทำมาจาก `assessment_attempts` สำเร็จมาจาก `results` ไม่ปนกัน |
| ผลไม่สมบูรณ์ | ไม่มีในตาราง `results` เลย (คำตอบระหว่างทำอยู่ในเครื่องผู้ใช้) จึงไม่ถูกนำมาวิเคราะห์ความเสี่ยง |
| เกณฑ์ความเสี่ยง | ใช้ `level` และ `band_label` ที่บันทึกตอนส่งคำตอบ ซึ่งคำนวณจาก `shared/assessments.ts` เดิม ไม่มีการคำนวณเกณฑ์ใหม่ |
| ข้อมูลส่วนบุคคล | ทุก API คืนเฉพาะจำนวนรวม ไม่มีอีเมล ชื่อ หรือคำตอบ (มี test ตรวจ) |
| กลุ่มเล็ก | ตัวเลข 1–(k−1) แสดงเป็น `<k` (k ค่าเริ่มต้น 5 ปรับได้ 5–50) พร้อม **secondary suppression** ดูหัวข้อท้าย |
| นับซ้ำ | การเปิดแบบประเมินเดิมซ้ำภายใน 24 ชม. นับเป็น attempt เดียว การเข้าใช้นับไม่เกิน 1 ครั้งต่อ 30 นาทีต่อคน |

## 2. ผู้ใช้งาน — `GET /api/admin/users?granularity=day|month|year`

| KPI | สูตร |
| --- | --- |
| ผู้เข้าใช้ต่อช่วงเวลา | `COUNT(DISTINCT user_id)` ต่อวัน/เดือน/ปีไทย |
| การเข้าใช้ต่อช่วงเวลา | `COUNT(*)` ต่อช่วง |
| ผู้ทำแบบประเมินต่อช่วง | `COUNT(DISTINCT user_id) results` ต่อช่วง |
| ผู้ใช้ใหม่ | `COUNT(*) users` ต่อช่วง |
| ผู้ใช้ที่กลับมาใช้ซ้ำ | คนที่มีการเข้าใช้ ≥ 2 **วันไทยที่ต่างกัน** ในช่วง |
| อัตรากลับมาใช้ | กลับมาใช้ซ้ำ ÷ ผู้ใช้งานในช่วง |
| ช่วงเวลาที่ใช้มากที่สุด | ชั่วโมงไทยที่มี `COUNT(*) usage_events` สูงสุด |
| อุปกรณ์ | จัดประเภทจาก User-Agent **ตอนบันทึก** เป็น mobile / tablet / desktop เก็บแค่ประเภท |

ระบบเลือก granularity อัตโนมัติ: ≤ 93 วัน = รายวัน, ≤ ~3 ปี = รายเดือน, มากกว่านั้น = รายปี ทุกช่วงเวลาถูกเติมเป็น 0 ไม่มีช่องว่างในกราฟ

## 3. สถิติแบบประเมิน — `GET /api/admin/assessments`

ต่อแบบประเมิน: เริ่มทำ, สำเร็จ (ครั้ง), ผู้ทำสำเร็จ (คน), ไม่สำเร็จ, กำลังทำ, อัตราสำเร็จ (สูตรเดียวกับข้อ 1 แต่กรอง `assessment_id`)
แบบที่นิยมที่สุด/น้อยที่สุด = เรียงจากจำนวนทำสำเร็จ ในกลุ่มที่เปิดใช้ · แนวโน้ม = `COUNT(*) results` ต่อช่วงต่อแบบ

## 4. ระดับความเสี่ยง — `GET /api/admin/risk?assessmentId=&granularity=`

| KPI | สูตร |
| --- | --- |
| จำนวนแต่ละระดับ (ต่อแบบ) | `COUNT(*) results GROUP BY band_label` ลำดับและช่วงคะแนนจาก `bandsFor()` (AUDIT-C แสดงช่วงชาย/หญิง) |

## 5. รายงาน — `GET /api/admin/reports/{usage|assessments|risk}.csv`

CSV แบบ UTF-8 มี BOM (Excel อ่านภาษาไทยได้) หัวรายงานมีชื่อรายงาน วันที่จัดทำ และช่วงเวลา · ป้องกัน formula injection · การส่งออกและการพิมพ์บันทึกลง `admin_audit`

## Small-cell suppression

1. ค่า 1 ถึง k−1 แสดงเป็น `<k`
2. **Secondary suppression:** ถ้าในกลุ่มที่แสดงยอดรวมมีช่องถูกซ่อนเพียง 1 ช่อง จะซ่อนช่องที่เล็กที่สุดถัดไปด้วย (ไม่อย่างนั้นคำนวณย้อนจากยอดรวมได้)
3. ถ้ามีระดับใดถูกซ่อน จะไม่แสดงสัดส่วน "ควรดูแล/เสี่ยงสูง" ของแบบนั้น
4. จุดในกราฟแนวโน้มถูกซ่อนเมื่อผลในช่วงนั้น < k หรือกลุ่ม "ควรดูแล" ในช่วงนั้นเป็นกลุ่มเล็ก
5. แบบที่มีผลรวม < k ซ่อนทั้งแถว

**ข้อจำกัดที่ยังเหลือ:** การนำตัวเลขจากหลายหน้าหรือหลายช่วงเวลามาลบกัน (เช่น ช่วง 1–31 กับ 1–30) ยังอาจทำให้รู้ค่าของกลุ่มเล็กได้ ซึ่งป้องกันได้ยากในแดชบอร์ดที่เลือกช่วงเวลาได้อิสระ จึงจำกัดการเข้าถึงไว้เฉพาะบัญชี admin/analyst และบันทึกการส่งออกทุกครั้ง

## ข้อมูลที่ไม่มีย้อนหลัง

`assessment_attempts` และ `usage_events` เริ่มเก็บตั้งแต่วันที่ deploy (บันทึกใน `app_settings.tracking_started_at`) ช่วงก่อนหน้ามีเฉพาะจำนวนที่ทำสำเร็จ แดชบอร์ดแสดงข้อความนี้ทุกหน้าที่เกี่ยวข้อง ไม่มีการเติมค่าประมาณ
